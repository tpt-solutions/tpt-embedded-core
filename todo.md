Two concrete paths were investigated on real hardware (user has esp32/esp32c3/esp32s3 boards):
  - `esp_hal::dma::m2m::Mem2Mem` (memory-to-memory pseudo-peripheral, the closest match to `DmaChannel`'s current abstract shape) only exists for esp32c2/esp32c6/esp32h2 — **not** esp32c3, esp32s3, or the original esp32. Not usable on any of the three boards available.

This confirms the underlying esp-hal DMA machinery genuinely works on this hardware; the remaining work is designing `EspHalBackend`'s API around a peripheral-attached shape (AES-DMA being the best-fit, wiring-free option) rather than the bare-buffer shape `DmaChannel::configure(buf, len)` currently implies. This is a breaking API change to `tpt-e-typestate-hal`, deliberately not made yet — it needs a real design pass (does `DmaChannel` become AES-specific? generic over a peripheral trait? esp32 has no equivalent path tested at all yet), not a quick patch.
  - **Design pass done, implemented, and flashed 2026-07-30**: rather than force AES-DMA (which necessarily transforms data) into the generic `DmaChannel<State, EspHalBackend>` abstraction (which promises an unmodified memory move — dishonest to implement with a cipher), added a second, concrete, peripheral-specific typestate type, `tpt_e_typestate_hal::aes_dma::AesDmaChannel<'d, State>` (new module `aes_dma.rs`), reusing the same `Idle → Configured → Transferring → Complete` markers from `state.rs` for API-shape consistency but with an AES-shaped `configure(mode, cipher_mode)`/`start(key, plaintext, ciphertext)` instead of the bare-buffer shape. `backend::EspHalBackend`'s generic stub is intentionally left as-is — it remains honestly unimplementable on esp32/c3/s3 (no hardware peripheral performs an unmodified memory move on these chips), not a leftover gap. Only compiled for `esp32c3`/`esp32c6`/`esp32s3` (mirrors esp-hal's own `AesDma` chip gate; plain `esp32` has no `AesDma` in esp-hal 0.22 at all). Because `esp_hal::aes::dma::AesDma`'s driver is fixed to `Blocking` mode and its `process()` call returns a transfer handle whose lifetime is tied to `&mut self` (a self-referential-struct problem to store across a movable `Transferring` value without extra `unsafe`), `start()` runs `process()` + `wait()` back-to-back internally and stores the outcome — no new `unsafe` was introduced by this module. **Verified on real hardware**: new firmware crate `firmware/typestate-aes-dma-smoke` (member of `firmware/Cargo.toml`) drives the same FIPS-197 Appendix B vector through `AesDmaChannel` itself (not raw esp-hal, unlike `aes-dma-smoke`) on a real ESP32-C3 — flashed, and `AesDmaChannel`'s ciphertext output matched exactly, proving the wrapper itself (not just the underlying esp-hal mechanism) is correct on real silicon. Compile-verified for the other two AES-DMA-capable chips too: `cargo build -p tpt-e-typestate-hal --target riscv32imac-unknown-none-elf --features "use_esp_hal,esp32c6"` succeeds; `esp32s3` (Xtensa) compile-check is blocked by the workspace-wide Xtensa toolchain gap documented immediately below, not by anything in this module.
  - **New finding 2026-07-30 — likely-broken CI for xtensa (esp32/esp32s3) build legs, workspace-wide**: while chasing the `esp32s3` compile-check above, discovered that **no Xtensa Rust toolchain version currently published by `espup`/`esp-rs/rust-build` can build this workspace's `esp-hal = "0.22"` pin at all**. Two failure modes bracket every tested version with no overlap: (a) newer toolchains (confirmed: `1.85.0.0` and later, including "latest") hard-error compiling `xtensa-lx-rt 0.17.2` (esp-hal 0.22's pinned dependency) — `asm! macro is not allowed in naked functions, use naked_asm! instead` — because upstream Rust tightened `#[naked]` function rules after `xtensa-lx-rt 0.17.2` was written; (b) older toolchains (confirmed: `1.83.0.1`, `1.84.0.0`) fail before even reaching that, because `indexmap`/`toml_edit`/`hashbrown`/`trybuild`/`proptest` (pulled in transitively — `trybuild`/`proptest` are this same crate's own dev-dependencies) resolve to versions requiring Cargo's `edition2024` feature, which only stabilized in upstream Rust `1.85.0` — the exact version where failure mode (a) begins. Root cause: this repo's root `Cargo.lock` is (correctly, for a library workspace) gitignored, so both locally and in CI, `cargo build` does a fresh "latest compatible versions" resolve every time — there is no pinned-in-the-past lockfile insulating older toolchains from newer transitive dependency releases. Since `build.yml`'s `esp32`/`esp32s3` matrix legs use the exact same unified workspace dependency graph (just via `esp-rs/xtensa-toolchain@v1` instead of `espup` directly), **this strongly suggests those two CI legs are currently failing** — not confirmed by directly observing a CI run (no `gh` CLI available in this environment to check), but reproduced twice locally across the full version range with zero satisfying overlap. Fixing this for real needs one of: pinning a `Cargo.lock` after all (reintroducing the usual downsides for a library workspace), or the larger, deliberately-deferred `esp-hal 0.22 → 0.23+` migration (which itself has its own breaking-API-change cost across every `use_esp_hal` code path in this workspace — see `firmware/hil-hello/README.md`'s "Known-good toolchain (ESP32-S3 / Xtensa)" section for what that migration involved for one single small firmware crate). Neither attempted here — flagging for a dedicated follow-up rather than a rushed fix to CI config under time pressure.

- [x] **BUG (fixed 2026-07-29)**: `ring_buf.rs` `RingBuf` is unconditionally `unsafe impl Sync` with safe `&self` `push`/`pop` and no compile-time single-producer/consumer enforcement — the exclusivity invariant is documentation-only ("ISR interleaving is prevented by the caller"). All existing tests pass unchanged (no test previously exercised `MessageType::Ack` inbound handling, so the event-type change was a safe, zero-regression addition). Cross-compiled clean for `riscv32imc-unknown-none-elf` (ESP32-C3). **Still open**: `Ack`/`Data` correlation only ties to the *sending* node's own `pending_acks` — there is still no cross-node retransmission-on-timeout or duplicate-detection; a lost `Ack` leaves the sender's `pending_acks` entry stuck forever (bounded by `MAX_PENDING_ACKS`, so it self-limits, but never resolves). That's real reliability work, deliberately out of scope here.
